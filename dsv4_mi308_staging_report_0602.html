DSV4-Pro MI308 / gfx942 — Pollution + RoPE + FP8 fix Report

1. 目前修復內容Summary

  • FP8 cast 格式：fused compressor Triton kernel 寫入 KV cache 時的 cast 格式從 IEEE E4M3 (tl.float8e4nv) 改成 AMD bias-8 E4M3 (tl.float8e4b8)，避免 mantissa 截斷。
  • RoPE position floor：移除 (position // 128) * 128 的 floor，每 token 用真實 position 對應的 rotary 角度。
  • ROCm RMSNorm + FP8 fused tie boundary：fused kernel 強制 float → scalar_t → float round-trip，匹配 unfused composite 在 E4M3 tie 上的行為。
  • ATOM Triton FP4 SiLU MoE：cudagraph-safe MXFP4 MoE backend（routed stage1/2 + active-expert metadata）。
  • Sparse MLA backend：split-K nope/rope 拆段、prefill chunk topk 處理，配合 gfx942 sparse attention kernel。

3. 仍待調查的點

下一個懷疑點：--enable-prefix-cache + 殘餘 drift / instability

觀察：

  • 有開 prefix cache 連跑兩次 GSM8K LIMIT=16：曾經看到 fresh 0.9375 → post1 0.75（掉 3 doc），server log 顯示 prefix cache hit rate 從 0% 跳到 18.9%，run1 的 KV blocks 被 reuse。
  • 過去 patched server --no-enable-prefix-caching 設定下：也看過 fresh 0.8125 → post1 0.9375（多答對 2 doc，反而上升），且 wrong-doc set 在 cold→warm 之間反覆翻動。意味著 LIMIT=16 + 8-shot fewshot 的 evaluation 本身有 ±0.0625 ~ ±0.1875 的 sampling 雜訊。

單一 0.9375 → 0.75 觀察不能直接歸因於 prefix cache pollution，要先關 prefix cache + 重複多次量化 instability 範圍，才能判別「真的有 drift 累積」vs「只是 sampling variance」。如果關掉 prefix cache 後仍方向性下降，則往 Lightning Indexer / MoE expert routing 兩個尚未排除的 drift 源頭追。

4. 其他性能分析

4.1 MAX_NUM_BATCHED_TOKENS 與 acc 的 trade-off

過去實驗中發現提高 MAX_NUM_BATCHED_TOKENS（從 default 1024 拉到更大）可以降低 prefill TTFT、改善整體 wall-clock， 但在 GSM8K LIMIT=16 上會出現方向性下滑。

TTFT / throughput 對 MAX_NUM_BATCHED_TOKENS 的 sweep（0520 的數據，在 acc 污染修補（FP8 cast / RoPE / RMSNorm round-trip）之前，bench 配置 random 10240 / 512 / np=2 / c=2）：

log: logs_0520_test_full/vllm_tp8_deepseek_v4_pro_client_running_0520{2058,2128,2142,2155}.log。 acc 確切數字請參考歷史紀錄；本表僅作 perf 趨勢與「acc 會掉」的方向性提示。

TTFT 從 47s → 23s（砍 51%），Total throughput +18%。但 acc 在 2048+ 走方向性下滑。 診斷時對較大 batch 做 routed MoE compare：cosine 趨近 1.0，但個別 element max_abs 仍偏大， 意味著聚合方向沒問題、但個別 logit 已經偏離過多。所以拉高 batched-tokens 的 TTFT 改善是付出 acc 的代價換來的， 不能直接調作 accuracy-stable 的主線設定。

進一步追蹤方向：(a) 用本次 patch（FP8 cast / RoPE / RMSNorm round-trip）後的 image 重跑同一組 sweep，看 acc 下滑是否被 patch 修掉，TTFT 收益就可以白拿； (b) 在較大 batch 下逐個關閉 ragged / offset-grid / deterministic-reduce，看是哪個環節在 batch 增大時數值不穩； (c) 試大 batch + CONC=1 配合 chunked prefill 重切，避免 single-batch 內 routed accumulation 過長； (d) 比對不同 MAX_NUM_BATCHED_TOKENS 的 wrong-doc set，看哪些 doc 是大 batch 才壞，可以反推 fp8 drift 的觸發條件。

4.2 --enable-prefix-caching 與 acc 的 trade-off

延續 §3 的懷疑點，在套 patch 後的 image（yijuchen/private:eveline_dsv4_fix_pollution_rope_staging_0602）做了對照測試，bench 配置同樣 random 10240 / 512 / np=2 / c=2，server 設定其他都一樣，只切 prefix cache 開 / 關：

SettingMean TTFTMean TPOTOutput thrptTotal thrptGSM8K（連跑兩次）
--enable-prefix-caching
（default）		 25,948 ms 562 ms 3.25 tok/s 68.18 tok/s fresh 0.9375 → post1 0.75（掉 3 doc）
--no-enable-prefix-caching 68,832 ms 548 ms 2.92 tok/s 61.27 tok/s 兩次都 0.875（不掉）

log:
  • with prefix cache: logs_0602_test_image_0602/vllm_tp8_deepseek_v4_pro_client_running_06030229.log
  • no prefix cache: logs_0602_test_image_0602_disprex/vllm_tp8_deepseek_v4_pro_client_running_06030312.log（acc log 同目錄）

結果非常乾淨地證實 §3 的懷疑：

  • prefix cache 對 TTFT 的收益巨大：68.8s → 25.9s，砍 62%（10240 input 的 prefill 大半被 cache 命中），Total throughput +11%。
  • 但 prefix cache 也是 acc drop 的放大器：開了之後 fresh 0.9375 → post1 0.75；關掉後兩次都 0.875、無方向性下降。
  • TPOT 兩個情境差不多（562 vs 548 ms），確認 prefix cache 主要影響的是 prefill 階段。

所以目前這份 patch 本身對連續跑（在無 prefix cache 下）已穩定，acc drop 是 prefix cache reuse 把殘餘 fp8 drift 累積到下一輪 fewshot prefix 上造成的。下一步要做的是：

  1. 用「open prefix cache + 重啟 server 跑 run2」做對照組——若兩次都 0.9375 → 確認 cache reuse 是唯一誘因；若仍掉 → 可能還有 KV blocks 之外的 drift channel。
  2. 調查 prefix cache hit 區段的 KV block fp8 累積誤差，看是否能在 patch 內加上「prefix cache eviction on long-decode boundary」之類的 mitigation，使 prefix cache 收益可以白拿。

5.2 GSM8K accuracy（fresh / post）

連跑兩次同一個 lm_eval 指令——第一次是 fresh，server 不重啟立刻跑第二次就是 post1（看 wrong-doc set 變化）：

lm_eval \
  --model local-completions \

  --batch_size auto \
  --tasks gsm8k \
  --num_fewshot 8 \
  --limit 16 \
  --log_samples \
  --output_path /data/results_conc_2_fewshot_8_limit_16_gsm8k \

跑完後輸出目錄會有 results_*.json + samples_gsm8k_*.jsonl。 要驗 instability 範圍：把同樣指令跑 3-5 次，每次的 strict-match / flexible-extract 一起看，能直接量出 ±0.0625 ~ ±0.1875 的 sampling 雜訊區間。
