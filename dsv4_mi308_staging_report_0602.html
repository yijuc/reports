1. 目前修復內容Summary

  • FP8 cast 格式：fused compressor Triton kernel 寫入 KV cache 時的 cast 格式從 IEEE E4M3 (tl.float8e4nv) 改成 AMD bias-8 E4M3 (tl.float8e4b8)，避免 mantissa 截斷。
  • RoPE position floor：移除 (position // 128) * 128 的 floor，每 token 用真實 position 對應的 rotary 角度。
  • ROCm RMSNorm + FP8 fused tie boundary：fused kernel 強制 float → scalar_t → float round-trip，匹配 unfused composite 在 E4M3 tie 上的行為。
  • ATOM Triton FP4 SiLU MoE：cudagraph-safe MXFP4 MoE backend（routed stage1/2 + active-expert metadata）。
  • Sparse MLA backend：split-K nope/rope 拆段、prefill chunk topk 處理，配合 gfx942 sparse attention kernel。

3. 仍待調查的點

下一個懷疑點：--enable-prefix-cache + 殘餘 drift / instability

觀察：

  • 有開 prefix cache 連跑兩次 GSM8K LIMIT=16：曾經看到 fresh 0.9375 → post1 0.75（掉 3 doc），server log 顯示 prefix cache hit rate 從 0% 跳到 18.9%，run1 的 KV blocks 被 reuse。
  • 過去 patched server --no-enable-prefix-caching 設定下：也看過 fresh 0.8125 → post1 0.9375（多答對 2 doc，反而上升），且 wrong-doc set 在 cold→warm 之間反覆翻動。意味著 LIMIT=16 + 8-shot fewshot 的 evaluation 本身有 ±0.0625 ~ ±0.1875 的 sampling 雜訊。

單一 0.9375 → 0.75 觀察不能直接歸因於 prefix cache pollution，要先關 prefix cache + 重複多次量化 instability 範圍，才能判別「真的有 drift 累積」vs「只是 sampling variance」。如果關掉 prefix cache 後仍方向性下降，則往 Lightning Indexer / MoE expert routing 兩個尚未排除的 drift 源頭追。

4. 其他性能分析

4.1 MAX_NUM_BATCHED_TOKENS 與 acc 的 trade-off

過去實驗中發現提高 MAX_NUM_BATCHED_TOKENS（從 default 1024 拉到更大）可以降低 prefill TTFT、改善整體 wall-clock， 但在 GSM8K LIMIT=16 上會出現方向性下滑。 診斷時對較大 batch 做 routed MoE compare：cosine 趨近 1.0，但個別 element max_abs 仍偏大， 意味著聚合方向沒問題、但個別 logit 已經偏離過多。所以拉高 batched-tokens 的 TTFT 改善是付出 acc 的代價換來的， 不能直接調作 accuracy-stable 的主線設定。

進一步追蹤方向：(a) 在較大 batch 下逐個關閉 ragged / offset-grid / deterministic-reduce，看是哪個環節在 batch 增大時數值不穩； (b) 試大 batch + CONC=1 配合 chunked prefill 重切，避免 single-batch 內 routed accumulation 過長； (c) 比對不同 MAX_NUM_BATCHED_TOKENS 的 wrong-doc set，看哪些 doc 是大 batch 才壞，可以反推 fp8 drift 的觸發條件。
